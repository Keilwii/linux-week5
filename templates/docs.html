Request path

browser ──HTTP 80──▶ nginx (the existing week-1 site, one extra include line)
                       ├── /viikko2/  /viikko3/  /    earlier weeks, unchanged
                       ├── /viikko5/static/  ──▶ files from /opt/viikko5/app/static
                       └── /viikko5/  ──unix socket /run/viikko5/gunicorn.sock──▶
                                        gunicorn + Flask (user viikko5)
                                           ├──HTTP──▶ Ollama 127.0.0.1:11434 (llama3.2:1b)
                                           └──socket─▶ MariaDB, database viikko5

GitHub Actions ──SSH 22──▶ deploy@A  (forced command: rsync or "deploy <sha>", nothing else)

Nginx strips /viikko5 and sends it in X-Forwarded-Prefix. Flask's ProxyFix turns that into the script root, so url_for() makes links like /viikko5/static/chat.js and the page tells the JavaScript its base path in <body data-base="/viikko5">. Nothing has the path hard-coded except the nginx snippet.

The reply is streamed: Ollama sends one JSON line per token, Flask passes each line on as soon as it arrives, nginx has proxy_buffering off for this location, and the browser reads the stream with fetch() and adds the tokens to the message.

Every browser gets a random id in an HttpOnly cookie chat_session (path /viikko5/, no expiry, so it lasts until the browser is closed). Messages are saved with that id, and the page loads the history from MariaDB on every load. Another browser or a private window has no cookie, so it gets a new id and an empty conversation. "Start a new conversation" just gives a new id.

Pipeline

File: .github/workflows/ci-cd.yml.

On every push and pull request (job "Lint and tests")

  • ruff check .
  • pytest -v, 17 tests. Ollama is replaced with a fake requests.post that returns ready NDJSON lines, and the database functions with an in-memory fake, so the runner needs neither.
  • bash -n for every script in scripts/.

On a push to main, only if the test job passed (job "Deploy to server A")

  1. Write the private key and the server's host key from the secrets SSH_PRIVATE_KEY and SSH_KNOWN_HOSTS (StrictHostKeyChecking yes, so a different server is refused).
  2. rsync --delete the code to /opt/viikko5/app as user deploy.
  3. ssh deploy@A "deploy $GITHUB_SHA" runs scripts/deploy.sh: installs requirements.txt into /opt/viikko5/venv, writes the SHA to REVISION, then sudo viikko5-install which applies deploy/sql/schema.sql, copies the nginx snippet and runs nginx -t (the old snippet is put back if the test fails), copies viikko5.service, daemon-reload, restarts only viikko5 and reloads nginx.
  4. deploy.sh waits until http://127.0.0.1/viikko5/health returns the new SHA, otherwise it prints systemctl status and exits with an error.
  5. The workflow then checks from outside: /viikko5/health must equal github.sha, the chat page, chat.js and /docs must load, and so must /, /viikko2/ and /viikko3/ from earlier weeks. Any failure makes the run red.

The app reads REVISION once when it starts. If it read the file on every request, the old process would already show the new SHA after the rsync, and the check would pass even if the restart failed.

GitHub Actions and SSH: the runners come from changing IP addresses, so I can't limit port 22 to them. Port 22 was already open to everyone in ufw (Hetzner, no extra cloud firewall). What protects it: password login and root login are off, fail2ban is running, and the deploy key can't get a shell. The weak point is that anyone who can push to main can change the nginx snippet and the systemd unit that root installs. viikko5-install refuses a unit that is not User=viikko5 / Group=viikko5 or uses +/! exec prefixes, but the repository is still trusted, so only I have write access to it.

How /viikko5/ was added to nginx

The existing site /etc/nginx/sites-available/week-1 got one line, next to the week 2 one: 

	include snippets/viikko2.conf;
	include snippets/viikko5.conf;

The setup script saved a copy to /root/week-1.before-viikko5 first, ran nginx -t and would have restored it on failure. The snippet (deploy/nginx/viikko5.conf in the repo) has only location blocks: = /viikko5 redirects to /viikko5/, ^~ /viikko5/static/ is an alias to the files on disk, and ^~ /viikko5/ proxies to the socket. Deploys only replace the snippet, never the site file. The Unix socket can't clash with week 2's port 8002.

Model, memory and disk

Before installing: 7.6 GiB RAM (6.9 GiB available), no swap, 4 vCPUs, no GPU, 70 GB free disk. I picked llama3.2:1b (1.3 GB on disk, about 1.5 GB in memory). It fits easily, so no swap or resize was needed, and it writes better English than the 0.5B models. Replies take about 3 to 4 seconds on the CPU. Ollama has OLLAMA_KEEP_ALIVE=24h so the model stays loaded and the first message isn't slow.

Is the chat database replicated to server B?

No. In week 4 B was set up with replicate_wild_do_table=week2.%, so it only applies changes to the week 2 counter. The viikko5 database, its users (created with sql_log_bin=0) and its messages are not applied on B. The table and inserts do go into A's binlog and travel to B over SSL, but B's filter drops them. I left it that way on purpose: B's page only needs the counter, chat messages are users' private text that shouldn't be copied to a second public server, and the week 4 replica didn't need changes. Replication was checked after the first deploy and after the reboot: both threads Yes, no errors.

Problem I solved

The first systemctl status viikko5 showed [ERROR] Control server error: [Errno 13] Permission denied: '/home/viikko5'. The chat still worked, so I almost missed it. Gunicorn 27 (the version pip installed) opens a control socket in ~/.gunicorn/ by default, but my service user has no home directory on purpose, and ProtectHome=true would block it anyway. I don't need the control interface, so I added --no-control-socket to ExecStart in deploy/systemd/viikko5.service and pushed. The pipeline installed the new unit, ran daemon-reload and restarted only viikko5, and the error is gone. It also showed that the systemd config really is deployed from the repository.

Something I learned: my first version of /health read the REVISION file on every request. That would make the health check lie, because the file is written before the restart, so a broken new version would still look deployed. Now the value is read once at startup.
